§2

What you are licensing

API first, AI first. Everything below is reachable by your engineers and by the agents they point at it. Not a roadmap - the MCP server, Opey and the signal channels are in the codebase and used today.

  • OBP API900+ REST endpoints across API versions up to v7.0.0 - accounts, transactions, payments, counterparties, views, consents and entitlements.
  • StandardsOpen Bank Project ships with OBP, UK Open Banking and Berlin Group NextGenPSD2. Conformance to your local market's standard is quoted work.
  • Connectors you switch by configWhere the data actually comes from is one setting: the built-in mapped store, REST, RabbitMQ, Akka, stored procedures or gRPC. Start on the built-in store, move to a real core later, without rewriting the API layer above it.
  • Dynamic connectorsWrite a connector method at runtime in Scala or Java and it takes effect without a redeploy. Each one passes maker-checker approval before it can execute.
  • Dynamic entitiesName an entity, give it fields, and it gets endpoints, stored records and a place in the live documentation - without anyone writing Scala.
  • Dynamic endpointsWrap a service of your own as OBP endpoints, with the same auth, rate limiting and generated docs as everything else.
  • MCP serverOBP-MCP puts the API in front of AI agents - Claude Code, Claude Desktop, IDE agents - over MCP, with tag-based routing, glossary access and the consent handshake handled when a call needs one.
  • Consent-based on-behalf-of accessAn agent is a consent user with its own long-lived consent, never a human's credentials. OBP checks the agent's own permissions, and records the person it acts for on every call, so anything durable the agent creates is owned by that person and the audit trail shows both who asked and who acted. The agent never becomes the human.
  • OpeyAn AI assistant that sits in the portal, reaches the API through MCP on the user's behalf, and asks for consent when a call requires it.
  • Signal channels for agent discoveryNamed channels on the instance where agents announce themselves, find each other and coordinate, without you building a message bus.
  • API Manager & ExplorerConsumer onboarding, key management, rate limiting, scopes, entitlements, and resource docs generated from the running API.
  • Consent and SCAConsent requests, consent lifecycle and expiry, with an audit trail over both.
  • Compliance and auditEvery call recorded, JWS request signing for non-repudiation, maker-checker approval on dynamic changes, and attribute-based rules deciding who can do what. The audit trail arrives with the platform rather than being bolted on afterwards.
  • Community chatChat rooms built into the portal. The developers building on your APIs talk to each other and to you inside the instance, so you do not have to stand up a Discord to have a community.
  • Blockchain ConnectivityProven approaches and open source components to connect the OBP platform to Cardano or Ethereum based chains.
  • Open source underneathNothing here is a black box you cannot read. You hold the code and you run the cluster, so you are never dependent on us to keep operating or to change something. Your copy ships from a private repository and stays private, which is what the commercial licence buys you.

You do not need a banking licence to need a bank's plumbing. Accounts, balances, transactions, consent, and an API over all of it: the same problem for a digital bank, a payments company, a marketplace moving money for other people, and a climate startup settling carbon credits. Open banking compliance is one thing you can switch on.

§3

Why two half days is enough

Because the platform is already built and battle tested - by banks, by fintechs, and by developers working at the edge of what agents can do. What you are handed is 900+ documented endpoints, a sandbox to develop against, and live documentation generated from the running API. The hard part happened before you arrived.

  • Day one is spent making calls. Your engineers get a sandbox with data in it and a developer portal, not a deployment guide and a wiki.
  • Agents do the reading. Point Claude Code or an IDE agent at our MCP server and it has the endpoints, the tags and the glossary. Your team can ask for what they want built instead of learning the whole API first.
  • The extension points do not go through us. Dynamic entities, dynamic endpoints and dynamic connectors are defined at runtime through the API. Adding your own data model or wrapping a service of your own needs no fork, no pull request and no release of ours.
  • And underneath it is a codebase already running inside regulated institutions in more than one jurisdiction, and everything we have learned since 2010 about which problem comes next.
